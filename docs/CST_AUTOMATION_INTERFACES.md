# CST Automation Interfaces and Project-File Evidence

Updated: 2026-07-12

Audited CST generation: CST Studio Suite 2026

Primary official source: `D:\CST2026\CST Studio Suite 2026\Online Help`

This is the maintained inventory of CST automation surfaces discovered for the project. It deliberately separates official interfaces, repository-verified wrappers, and observed internal project files.

## 1. Evidence classes

| Class | Meaning | Allowed use |
| --- | --- | --- |
| `OFFICIAL` | Explicitly documented in local CST 2026 Online Help supplied/audited for this project | May be wrapped with tests and live validation |
| `TUTORIAL` | Used in an official CST tutorial but not found as a full API-reference entry | Inspect installed library and live-test before general wrapper |
| `REPO-VERIFIED` | Existing repository wrapper or exact RF-CEM path has worked in controlled live CST | Reuse within its stated version/scope; do not generalize silently |
| `OBSERVED-INTERNAL` | Found in an unpacked CST project or generated by CST, not documented as public API | Read-only evidence by default; version-sensitive; explicit provenance |
| `INFERENCE` | Combination of official facts that has not been live-tested in the exact form | Disposable-project experiment only |
| `UNVERIFIED` | Plausible name/behavior without adequate evidence | Do not implement or call |

Core rule: method names are not evidence. Do not guess `cst.interface`, `cst.results`, VBA, COM, command-line flags, or internal file formats.

## 2. Official interface overview

The official CST 2026 automation surfaces relevant to this repository are:

1. command-line batch mode;
2. OLE/COM Application Object;
3. 3D Simulation VBA Project Object;
4. Design Studio VBA Project Object;
5. Python `cst.interface`;
6. CST-integrated Python scripts and Generic Command JSON;
7. VBA project/global/control/structure macros;
8. Python `cst.results`;
9. project-local `Model.run` batch hook.

They solve different problems. `cst.interface` controls a live DesignEnvironment; `cst.results` reads saved results; direct unpacked files provide additional evidence but are not a replacement public API.

### 7.7 `RunScript` through Python

Evidence: `INFERENCE`.

Two official facts exist:

1. Python can execute VBA through `Model3D.add_to_history` or `Schematic.execute_vba_code`;
2. the VBA project object has `RunScript` and `RunMacro`.

Candidate bridge:

```python
project.model3d.add_to_history(
    "run external script",
    'RunScript "C:\\path\\driver.bas"',
)

project.schematic.execute_vba_code(
    'RunScript "C:\\path\\driver.bas"'
)
```

This exact composition must be live-tested on a disposable project before production use. It may add unwanted 3D history.

## 9. Official macro concepts and storage

Evidence: `OFFICIAL`.

Audited pages cover:

- VBA macro language overview;
- project/global macros;
- store/import/edit/move/delete dialogs;
- History List;
- preloaded macros;
- user-defined postprocessing macros.

Confirmed concepts:

- VBA programs require `Sub Main`;
- macros can be project-local or global;
- macro names can use submenu syntax;
- control macros orchestrate calculations and are generally not added to model history;
- structure macros use `.mcs` and append construction commands when run from the Macros menu;
- History List can be converted into a new project macro;
- CST installs preloaded global macros;
- user-defined postprocessing `.BAS` files may live under a global library macro path with names such as `0D-Result_*.BAS` and `1D-Result_*.BAS`.

The GUI “Import VBA Macro” behavior is documented. A standalone import API was not found.


Confirmed capabilities:

## 13. `Model/3D/ModelHistory.json`

Evidence: `OBSERVED-INTERNAL`, used read-only by repository.

Observed top-level fields:

- `general`: version, units, frequency and other project metadata;
- `history`: ordered entries.

Common history-entry fields:

- `caption`;
- `version`;
- `hidden`;
- `type`;
- `code`.

Repository reader:

```text
src/cst_history_extractor/history_reader.py
```

Uses:

- UTF-8 with BOM tolerance;
- entry order;
- exact VBA code preservation;
- type/hidden counts;
- provenance and explicit limitation message.

Limitations:

- not a documented Python API;
- may be absent until CST opens/unpacks the project;
- does not necessarily contain postprocessing template registration;
- content may not represent current unsaved GUI state;
- parser must preserve unknown fields/commands;
- never write it as a generic automation mechanism.

## 14. `Model/3D/Model.rpp`

Evidence: `OBSERVED-INTERNAL` plus `REPO-VERIFIED` for the exact 500 MHz path.

Role: registry used by CST Template Based Post-Processing UI/framework to recognize result-template artifacts.

Repository behavior:

- reads source registry as text;
- verifies the observed record-line count;
- selects only Frequency, R/Q and Q template records;
- writes a filtered target registry;
- if source registry is absent, can emit a minimal registry built from metadata verified in the 500 MHz live path.

Important:

- copying `.r0d` files alone was insufficient for stable registration;
- the fallback registry format is not a generic CST specification;
- do not synthesize arbitrary records;
- use only for the exact verified CST 2026 template family until revalidated.

## 15. `.r0d` and `.r1d` result-template artifacts

Evidence: `OBSERVED-INTERNAL` plus `REPO-VERIFIED` copying for three `.r0d` templates.

Observed properties:

- mixed binary/text internal artifacts;
- associated with 0D/1D template-based postprocessing;
- not documented as a public file format;
- names and registry records are significant.

Verified RF-CEM template set:

```text
Frequency (Mode 1).r0d
R over Q (Mode 1).r0d
Q-Factor (Perturbation) (Mode 1).r0d
```

Policy:

- do not decode or edit binary semantics;
- copy from a known verified source project;
- register via matching `Model.rpp`;
- open/save through CST;
- verify actual result-tree paths and values;
- retain source path/hash/version provenance.

`.r1d` may be scanned as read-only evidence for other result templates, but no generic production reader is established.

## 16. `Model/PC_integration.json`

Evidence: `OBSERVED-INTERNAL` plus bounded RF-CEM use.

Observed role: process/integration input and output variable metadata.

RF-CEM merges these output variable names:

```text
3D\Frequency (Mode 1)
3D\R over Q (Mode 1)
3D\Q-Factor (Perturbation) (Mode 1)
```

CST may rewrite this file on save. It is secondary diagnostic evidence; template-file presence, registry and result-tree readback are stronger checks.

Do not treat its schema as a stable public contract.

## 17. `Result/Postprocessing.log`

Evidence: `OBSERVED-INTERNAL`.

Use:

- read-only diagnostic of postprocessing activity/errors;
- correlate template evaluation with project/result state;
- retain raw text and project provenance.

It is not a structured success contract. A missing or ambiguous line cannot replace result-tree validation.

## 18. Result-tree paths

Evidence: `REPO-VERIFIED` through `cst.results`.

RF-CEM required scalar paths:

| Metric | Tree path | Unit/definition |
| --- | --- | --- |
| Frequency | `Tables\0D Results\Frequency (Mode 1)` | MHz in current template |
| R/Q | `Tables\0D Results\R over Q (Mode 1)` | ohm |
| Q perturbation | `Tables\0D Results\Q-Factor (Perturbation) (Mode 1)` | dimensionless |

Never infer units solely from the tree-path string. The workflow/template contract supplies units and should validate numeric range/finiteness.

`Model3D.get_tree_items` and `cst.results.get_tree_items` expose different contexts. Neither returns full existing history bodies.

## 19. Verified RF-CEM CST path

Evidence: `REPO-VERIFIED` on workstation/CST 2026.

Sequence:

1. generate deterministic action list from reviewed UDSG, expert prior, STEP and extracted history templates;
2. connect to dedicated DesignEnvironment;
3. create new MWS project;
4. execute units history block;
5. define Copper (annealed) background:
   - conductivity `5.8e7 S/m`;
   - geometry units mm;
   - frequency units as specified in template;
6. import generated STEP;
7. assign imported body to `Vacuum`;
8. apply boundary block;
9. apply frequency range;
10. apply Tetrahedral eigenmode solver history blocks;
11. save project;
12. install `Model.rpp` and three `.r0d` artifacts;
13. merge `PC_integration.json` variables;
14. reopen/save;
15. run synchronous solver;
16. save results;
17. read required result-tree scalars.

Representative verified output:

```text
Frequency = 505.583944055 MHz
R/Q      = 428.086330643 ohm
Q        = 45867.1264209
```

This verifies one automation chain. It does not establish universal CST template portability or RF equivalence of all generated geometries.

## 20. `EvaluateResultTemplates` behavior

Evidence: command executed through existing `CSTProject.execute_vba`; live behavior is mixed.

Current implementation can execute:

```vb
EvaluateResultTemplates
```

On the Tetrahedral RF-CEM path this may produce `HEX mesh is invalid` even when solve and result-tree readback succeed.

Policy:

- disabled by default in the campaign;
- do not auto-switch to HEX;
- inspect registration, material assignment, old result state and solver completion;
- prefer required result-tree readback when templates already evaluate automatically;
- treat the message as diagnostic, not automatically fatal or harmless.

## 23. Known unknowns

Still requiring live validation or authoritative documentation:

- exact `RunScript(absolute_path)` behavior when called inside a 3D `add_to_history` block;
- side effects/history entry behavior of that bridge;
- exact `RunMacro` naming for submenu/global macro paths;
- combined command-line `.cst` plus `.bas` invocation;
- safety of `-hide` for every workflow operation;
- actual global/user macro directories on this installation;
- stability of `Model.rpp` record structure across CST versions/templates;
- generic meaning/portability of `.r0d/.r1d` internals;
- whether every project reliably creates `ModelHistory.json` after open/save;
- full public status of tutorial `get_current_project` in installed libraries;
- native `StoreParameter` Python member status/signature used by the compatibility wrapper;
- robust field/mode-shape export contract for RF-CEM comparison.

Unknowns must stay explicit. Do not resolve them with method-name guesses.

## 24. Prohibited shortcuts

Do not:

- import a guessed `cst.interface` member;
- parse `.r0d/.r1d` binary values as if documented;
- edit `ModelHistory.json` to control CST;
- copy only `.r0d` and assume templates are registered;
- read results before saving the project;
- trust cached `ProjectFile` after a new save without invalidation;
- treat GUI tree paths as history bodies;
- switch Tetrahedral to HEX because of one postprocessing message;
- run global process cleanup as routine shutdown;
- delete project locks without verifying process ownership;
- commit CST projects, unpacked result folders or local configuration;
- present observed internal formats as official APIs.
