Customize Python functionality¶

CST Allows full customization of the python menu and what is being executed. This is done in the form of a Generic Command. We will start with a very basic example and a more advanced example setting up a custom python venv with some functionality associated with it.

The section Generic Commands can be used as a reference for creating Commands.

Minimalistic example¶

Let’s consider a simple example to get started with a Command. Create a file named my_favorite_editor.json in one of your configured library path (or add a new one) according to the scheme below.

<library-path>
└── Commands
    └── my_favorite_editor.json

Edit the file and add:

{
    "name": "My Favorite Python Editor", // The name which will appear in the menu
    "program": "notepad", // assumes notepad(.exe) can be found by the operating system, replace this with an editor of your liking.
    "console": {
        "show": false // As this is a gui-application we suppress the console from popping up
    }
}

If you now run the Macros/Python -> Update Menu, a new entry should appear named My Favorite Editor. Clicking on it should launch notepad.exe as expected.

Customization of Macros/Python -> Run Script¶

Any python file – not starting with and underscore – placed under Python/scripts in any of the library paths, will automatically be listed in the Macros/Python -> Run Script sub-menu. By convention the sub menu entries are identical to the file names, with underscores _ replaced by spaces.

By default the Console will be shown during the execution of the python scripts and auto-close if no error occurred. This is done because – in general – these scripts are not expected to have a gui, but should simply perform one task and close again. In some cases you may want to override the default.

To enable that, there are two options:

  1. Put a json file named python_script_runner.json in the same directory as the script. Any settings in this file will override the defaults to all files in this folder.

  2. Put a json file named exactly like the python file (e.g. my_script.py -> my_script.json) next to the script. Any setting in this file will override the defaults for that script.

Example layout:

<library-path>
└── Python
    └── scripts
        └── python_script_runner.json   // applies to all scripts in this folder
        └── some_script.py
        └── my_script.py
        └── my_script.json              // applies to my_script.json
    ...

In this case the content of the two files could look like:

// python_script_runner.json
{
    "console": {
        "success_exit_delay": 5  // for keeping the console open long enough to read from it.
    }
}

and

// my_script.json
{   
    "name": "My Great Script", // overrides the name default naming `my script` -> `My Great Script`
    "restrict_to": {
        "caller": "schematic" // only shows the menu item if the menu is opened from a schematic view.
    },
    "console": {
        "show": false
    }
}

Working with a custom python interpreter/environment¶

CST ships with a fully functional python interpreter (version 3.12) located at ${CST_INSTALL_PATH}/Python which comes with many packages pre-installed. However, you may wish to create custom venvs in cases where other packages are needed or different versions of the ones we ship. In such cases you can create your own environment and run your python code with it. Consider the following example my_company.json and custom python script calculate_something.py stored as follows:

<MyCompanyPy Folder>
└── Commands
    └── my_company.json
    └── calculate_something.py

The json file contains:

{
    "name": "My Company",  // This is the top level-menu item
    "parameters": {
        "base_python_interpreter": {
            "win32": "${CST_INSTALL_PATH}{/}Python{/}python.exe",
            "linux": "${CST_INSTALL_PATH}/Python/bin/python"
        },
        "venv_path": "${CST_APPDATA_PATH}{/}my_company_venv", // Destination for the venv
        "scripts": {
            "linux": "${venv_path}/bin",
            "win32": "${venv_path}{/}Scripts"
        },
        "venv_interpeter": "${scripts}{/}python",  // the interpreter in the venv
    },
    "subcommands": [
        {
            "Create venv"
            "program": [
                "${base_python_interpreter}", "-m", "${venv_path}", "--clear",                          // creates the venv
                "&&",                                                                                   // and
                "${scripts}{/}pip", "install", "numpy", "scipy"                                         // installs the desired packages
                "&&",                                                                                   // and
                "${scripts}{/}pip", "install", "-e", "${CST_INSTALL_PATH_AMD64}{/}python_cst_libraries" // installs python cst libraries
            ]
        },
        {
            "name": "Run calculate_something",  
            "program": "${venv_interpreter}",                           // Runs the venv interpreter
            "args": ["${CST_COMMAND_DIR}{/}calculate_something.py"]     // on the script
        }
    ]
}

And the script calculate_something.py could contain something like:

import numpy as np
import scipy
import cst

from cst.interface import get_current_project

prj = get_current_project() # This uses the --cst-pid and --prj options to retrieve a handle to the current project.

...
# Code that does something with cst, numpy and scipy
...

This should create a new menu entry in the Macros/Python menu as:

My Company
    └── Create venv
    └── Run calculate_something

Now by first creating the venv via Create venv, the second command can be triggered via the menu.

If desired any other available python interpreter can be specified for creating venvs, this may even be required if you are using python code that is not compatible with the version of python provided. In that case just replace the value for base_python_interpreter with an interpreter of your choice.

Making your python functionality available to others¶

In case want to share your python functionality with other people within your company, you can do so in many ways. The best solution in your situation will depend on a number of variables like:

  • How many people will need the python code, and how often do they need to update

  • The size of the python project, a few single files or full fledged python packages

  • How often is the python code updated and how easy should it be for your users to receive updates

  • The restrictions put on you by your IT-department for sharing and hosting items

There is no one-size fits all solution, but with the total freedom given in the Commands, this should allow you to come up with a working solution in your situation. Nevertheless, we will discuss one of the easiest solutions in the next section.

Basic example for sharing python code¶

Probably the simplest case would be to have a shared folder on your corporate network. This folder can contain both the Commands and the associated python code. This layout is available as a template and can be found under ${CST_INSTALL_PATH}/Online Help/PythonTutorial/data/CustomPythonTemplates/BasicExample, please copy and adjust it to your needs.

<MyCompanyPy Folder>
└── Commands
    └── my_company.json
    └── requirements.txt  <- contains the required packages for your project
| src
    └── my_company
        └── hello_world.py
        └── example_script.py
        └── example_app.py

You can copy the template and adjust it to your liking, and then make it available to your users. If you decide to share this code directly via a network share, then be aware that that possibly slows down performance and can suffer from outages if used directly. In that case you may want to ask your users to copy the code to their local machine and use it from there.

All users only need to add <MyCompanyPy Folder> to the CST Studio Suite Library paths and that should make all menu items available.

Generic Commands¶

Json-files and Folder structure¶

A Command is essentially a json file which contains the instructions to start the desired application and putting it inside a folder named Commands (or subfolder thereof) inside one of the library paths registered in CST Studio Suite. The menu structure will follow the subfolder names first and then any internal hierarchies in the json definitions.

<library-path>
└── Commands
    └── my_first_command.json
    └── my_second_command.json
    SubFolder1
        └── my_nested_command.json
    SubFolder2
        └── my_nested_command.json
        ...
    ...

Fields¶

There are various fields that can be set in the json file to control how the command is executed.

  • "name": The name used for the command, which will appear in the menu.

  • "program": Two options: 1 If a single string is given, then this should be:

    • An absolute path to an executable

    • A string which the system can resolve to an executable according to the rules offered by the operating system. (e.g. relative to $PATH or current working directory). 2 If a list of strings is given, e.g. ["cmd1", "arg11", "arg12", "&&", "cmd2", "arg21", ..., "||", "cmdN"] the whole list is transformed into a single command line. Please refer to your operating system manual for more information on concatenating multiple commands with operators like "|", "||", "&", "&&". String arguments that contain spaces will be automatically surrounded with double quotes.

  • "args": A list of strings with the arguments to the "program". String arguments that contain spaces will be automatically surrounded with double quotes.

    • Note: Only use this field in conjunction with option 1 (a single string) for "program"

  • "cwd": The working directory in which the command should be run.

  • "report_command_line": (bool) controls whether or not the actual command line is printed into the active message window. (default: true)

  • "console": This should be an object with the following possible keys:

    • "show": (bool) determines whether or not a console should be shown. If this evaluates to false, all other keys become meaningless (default: true).

    • "pause_on_error": (bool) will keep the the console open in case an error occurred in the command execution (default: true).

    • "success_exit_delay": (int) will keep the the console for given number of seconds. Use this to provide ample time for the user to read output messages (default: 0).

    • "keep_open": (bool) will keep the the console open, and gives control to the console (default: false).

  • "restrict_to": This offers the ability to hide/show the command from the menu depending on the context

    • "platform": Single string, which should be either "win32" or "linux" to restrict to Windows or Linux systems respectively.

    • "project_type": Single string or list of strings, will only pop-up if the project-type matches (one of) the given values.

    • "caller": Single string or list of strings, will only pop-up if the project-type matches (one of) the given values.

  • "subcommands": A list of objects following this scheme for a Command. This will create sub-menu entries allowing you to structure your commands.

Hierarchy¶

When defining commands hierarchically, fields are principally inherited from the parent Commands. This can be used to conveniently pass on and override settings in lower level commands. Note that the parent command itself is no longer executable as soon as there are "subcommands". These serve only to create the menu structure and pass on settings to the lower-level commands.

{
    "name": "Hello Universe",
    "program": "python",
    "console": {
        "success_exit_delay": 5
    },
    "subcommands": [
        {
        //  "program": is inherited
            "name": "Hello Python World",
            "args": ["-c", "hello world!"]
        },
        {
            "name": "Hello CMD World",
            "program": "echo", // override python
            "args": ["goodbye world!"]
        }
    ]
}

Interpolation of variables¶

In many cases you will need to know the active project path, an environment variable or some other variable to pass to your command line. To accomplish that the strings containing ${variableName} in the json file will be interpolated before execution.

Predefined variables¶

The following list of predefined variables may be used in your Command.

  • "${CST_CALLING_APP}": The application starting the Command (e.g. model3d/schematic/pcbs)

  • "${CST_STUDIO_PID}": The PID of the CST Studio Suite DesignEnvironment launching the command

  • "${CST_INSTALL_PATH}": The installation path of CST STudio Suite

  • "${CST_INSTALL_PATH_AMD64}": The platform dependent subdirectory of "${CST_INSTALL_PATH}" containing most of the binaries (Windows: AMD64, Linux: LinuxAMD64)

  • "${CST_APPDATA_PATH}": The folder in the users’ home directory containing data related to CST Studio Suite. Windows: %LOCALAPPDATA%\CST AG\20XY Linux: $HOME/.local/CST AG/20XY

  • "${CST_VERSION}": The major version of CST Studio Suite, e.g. 2025

  • "${CST_DEFAULT_LOCAL_LIBRARY_PATH}": The first entry in the library paths

  • "${CST_COMMAND_DIR}": The directory in which the command json file lies

  • "${CST_ACTIVE_PROJECT}": The project from which the command was triggered

There are four special path related variables, which make it possible to define paths in a platform agnostic manner:

  • "{/}" and "{\}": This is replaced by / on Linux platforms and \ on Windows platforms.

  • "{:}" and "{;}": This is replaced by : on Linux platforms and ; on Windows platforms.

Note that these variables are not prefixed with a $-sign.

Environment variables¶

Any environment variable may be used as a variable in the interpolation. The interpolation scheme to enable this is

  • "${env:ENV_VAR_NAME}"

where ENV_VAR_NAME should be replaced by the desired environment variable.

Local Command variables¶

Further flexibility can be achieved by specifying local variables in the json file. This is done in an object named parameters, which contains key-value pairs that can be used for interpolation later. A value can be either a string, or an object. If an object is used, the key is used to differentiate the value for the available platforms (win32 and linux.). Consider the following example:

{
    //...
    "parameters": {
        "venv_path": "${env:MY_VENVS_ROOT}{/}my_venv",
        "scripts": {
            "linux": "${venv_path}/bin",
            "win32": "${venv_path}/Scripts"
        },
        "venv_python_interpreter": "${scripts}{/}python"
    },
    //...
    "program": "${venv_python_interpreter}",
    "args": ["-c", "print('Hello World')"],
    //...
}

The above snippet defines the variable ${scripts}, which gets interpolated depending on the platform as:

  • Windows: “${env:MY_VENVS_ROOT}/my_venv/Scripts”

  • Linux: “${env:MY_VENVS_ROOT}/my_venv/bin”

This in turn is used to define a platform agnostic path to the python interpreter inside the venv ${venv_python_interpreter}.

This functionality greatly improves portability between platforms, while maintaining a concise specification.
